# a94d4b28 — Fix xinput loading.

- **Date:** 2025-02-27  |  **Risk (A.1):** HIGH
- **Files:** 9 — Step2.UpdateDiStates (206-line rewrite), DInputHelper, ErrorsHelper, SettingsManager, WPF pad control, EngineHelper, JocysCom shared

## Changes

### Fixes
- `EngineHelper.GetMsXInputLocation` hard-coded `xinput1_3.dll` in the system
  folder. That file ships with the DirectX 9 redistributable, not with Windows;
  Windows 8 and newer only have `xinput1_4.dll` out of the box. The commit
  scans for `xinput1_?.dll` and takes the newest one.

### Refactor (not portable)
- Rewrites `UpdateDiStates` around cached mapped-device lists refreshed on a
  `SettingsChanged` flag, plus related plumbing across 8 more files.

## Backward compatibility for 4.17.x
The `EngineHelper` part applies directly. On a machine without the DirectX 9
redistributable, `GetDefaultDll(useMicrosoft: true)` called
`FileVersionInfo.GetVersionInfo` on the missing `xinput1_3.dll` and threw
`FileNotFoundException` before the caller's `Exists` check could run, so
Virtual (ViGEm) emulation failed to start. The version lookup in that branch
computed two locals that were never used, so it is dropped rather than guarded.
The upstream `.First()` throws when nothing matches; the port keeps the old
path as a fallback so the caller's existing `Exists` check still decides.

`Controller.ReLoadLibrary` loads by absolute path and resolves entry points
with `GetProcAddress`, so `xinput1_4.dll` loads exactly like `xinput1_3.dll`.
