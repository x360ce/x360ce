## Backward compatibility for 4.17.x
- Adds a new persisted option (schema-tolerant, not breaking).
- The subject undersells it: at 4.17.12 `SetProcessDPIAware()` was called
  **unconditionally**, which is what clips labels at 150% display scaling.
  This commit makes DPI-awareness opt-in with default **false**, so the app
  renders bitmap-scaled by default — slightly soft, but nothing clips.

## Decision
**Postpone** (final, after live testing on Windows 11 at 150% DPI). This commit
was ported, tested, and **reverted** the same day. Making the early
`SetProcessDPIAware()` call conditional (default off) breaks the WinForms line:
the app hosts WPF content, and WPF initialization flips the process to
DPI-aware mid-startup anyway — after WinForms already laid out at 96 DPI. The
result is an unscaled, tiny UI and an intermittent empty window title from the
handle churn during the DPI transition. The original 4.17.12 code calls
`SetProcessDPIAware()` unconditionally before any window exists — that stays.
Per user: the conditional-DPI design belongs to the later WPF rewrite; the
WinForms render fixes to port instead are [81ee19e2](81ee19e2.md) +
[11c47449]'s WinForms designer hunks (label clipping at high DPI).
